1. P0 — MAKE NON-SPLIT TAB ACTIVATION ONE REAL WPF TRANSACTION
==================================================

Current problematic shape at baseline:

- ContainerWindow.xaml.cs registers TabsListBox_PreviewMouseLeftButtonDown.
- While split is presented, that handler intentionally handles/swallow a normal TabViewModel click to prevent WPF selection ping-pong.
- ContainerWindow.SplitInteractionFix.cs separately registers another PreviewMouseLeftButtonDown handler with handledEventsToo=true in OnContentRendered.
- That second callback does another InputHitTest and tries to recover the click by calling SuspendPresentedPairForUserSelection.

This is fragile and is a likely reason the four-tab defect still survives despite deterministic policy tests.

Required architecture:

ONE authoritative routed-event path must own:

    pointer hit on ordinary non-member C/D
      -> classify target
      -> prevent premature ListBox selection
      -> journal-safe split suspension
      -> commit dormant split state
      -> switch model active tab
      -> position/show C/D once
      -> foreground C/D once

No "first handler swallows, second handledEventsToo handler recovers" design.

Preferred implementation:
- wire the split interaction preview handler during InitializeComponent/XAML or otherwise guarantee it runs before ordinary drag/selection logic;
- once it identifies a valid non-member click, set Handled=true and execute the canonical transition;
- ordinary drag handler must never see that already-owned interaction;
- remove the handledEventsToo recovery hook and duplicate second hit-test path.

Buttons, middle-click, right-click, split member halves, context menus, and drag affordances must retain their own behavior.

Mandatory real test:

    A+B split
    click C
    assert C visible/full content rect
    assert A hidden
    assert B hidden
    assert pair relationship still A/B dormant
    click A half/composite
    assert exact A/B pair resumes
    click D
    assert D visible
    repeat 50 cycles alternating C/D

Do this with actual WPF routed events / ValidationDriver real input, not only a pure policy object.

2. P0 — REMOVE DURABLE DISK I/O FROM TAB-CLICK HOT PATH
==================================================

Audit finding:

GroupManager.SwitchActiveTab currently makes active selection a synchronous durable state save.

PersistenceService.Save serializes state and performs backup/temp/atomic file writes synchronously.

WindowShepherdService.Hide also refreshes the recovery journal synchronously even though a successful capture already committed the complete capture-session recovery entry BEFORE the first presentation mutation.

The recovery journal uses deliberate durable disk semantics.

Therefore normal A->B switching can enter durable storage multiple times during the WPF input turn; split A/B->C can hide two guests and then persist state, multiplying the stall.

Fix this structurally.

A. Active tab persistence

Active selection is NOT a crash-recovery safety boundary.

- same index => true no-op
- active-index state save => debounced/coalesced
- ultimately move ordinary state.json writing off the dispatcher/UI thread

Preferred persistence design:

    UI thread:
      mutate authoritative model
      build immutable persisted DTO/snapshot
      enqueue generation N

    one background state writer:
      discard superseded generations
      write newest snapshot atomically
      update last-saved fingerprint
      never block tab/input/layout threads

On shutdown:
- bounded final flush of latest state if possible
- do not make normal focus/tab switching synchronous again

Keep capture/release recovery journal safety separate.

B. Recovery journal

Preserve the non-negotiable invariant:

    successful Capture
       -> durable complete rescue entry
       -> ONLY THEN first DWM/visibility/placement mutation

Once that capture-generation rescue entry is known durable, ordinary TabDock
SW_HIDE used for tab switching must NOT rewrite+fsync identical recovery JSON.

Track current capture generations whose rescue entry is durably committed.

Rules:
- JournalCapture success => rescue generation known durable
- ordinary JournalHide with same live generation => reuse known durable entry; zero disk write
- JournalMarkIntentionalHide success => invalidate "rescue known durable" for that generation
- if ownership is retained after an intentional-hide/release failure, a future ordinary hide must re-establish rescue intent before hiding
- JournalClear/release cleans bookkeeping
- legacy/loaded/recovery entries remain fail-closed
- never weaken identity/recovery semantics to gain speed

Add deterministic tests proving:
- 100 ordinary hides after one successful capture cause zero additional durable journal commits
- intentional-hide marker then retained ownership requires the rescue commit before a subsequent ordinary hide
- failed initial capture journal still blocks capture
- force-kill recovery after repeated background tab switches still rescues the guest correctly

3. P1 — FIX RELAYOUT EVENT AMPLIFICATION
==================================================

Audit the REAL ContainerWindow path.

Known issue #1:
RequestRelayout(ensureFinalPass:true) sets the "after pending" latch before
checking whether a render is already pending.

Correct invariant:

- idle + ensureFinalPass => ONE scheduled pass
- already pending + ensureFinalPass => pending pass + exactly ONE follow-up final pass

Apply this both to:
- live ContainerWindow logic
- PresentationLayoutCoordinator

Then make PresentationLayoutCoordinator the actual production scheduler rather
than leaving a duplicated test-only scheduler in ContainerWindow.

Known issue #2:
LayoutUpdated currently requests relayout on every WPF layout pass.

Replace with geometry-dirty behavior:
- compare actual physical ContentHost screen rect
- if unchanged within rounding epsilon => no RequestRelayout
- if changed => one coalesced render request
- reset/invalidate cached rect on DPI/topology changes as needed

Audit every current trigger:
- WM_WINDOWPOSCHANGING
- WM_WINDOWPOSCHANGED
- WM_EXITSIZEMOVE
- LocationChanged
- SizeChanged
- LayoutUpdated
- StateChanged
- CompositionTarget.Rendering
- foreground/reorder WinEvents
- guest move/size loop

For each logical frame, identify which trigger is authoritative and which are
fallbacks.

There must not be 3-5 different callbacks all independently re-gluing the same
geometry.

4. P1 — FIX SPLIT Z-ORDER CHURN
==================================================

At baseline, split layout treats the z-order as healthy only when:

    GetWindow(top, GW_HWNDNEXT) == bottom

That requires strict adjacency.

This is not a valid real-world invariant. IME windows, accessibility helpers,
shell overlays, GPU/driver helper HWNDs, and unrelated top-level windows can
legally exist between the two guests.

If geometry is already correct but a helper sits between the panes in z-order,
the current code can repeatedly issue a full PositionGuestsDeferred batch.

Replace strict adjacency with RELATIVE ORDER:

    focused/top split member occurs somewhere above partner
    partner occurs above/paired correctly relative to TabDock container

Then:
- if relative order is already healthy, only repair container pairing if needed
- do not reissue guest geometry
- do not fight unrelated HWNDs

Add a deterministic z-order seam/test where:

    top
    helper-1
    helper-2
    bottom
    unrelated
    container

is accepted as healthy pair order.

Also test:
- container accidentally between top/bottom => one z-order repair
- partner above focused member => one pair-order repair
- helper insertion/removal does not cause repeated PositionGuestsDeferred

10. FUNDAMENTAL SHEPHERD ARCHITECTURE CHECK
==================================================

Do not assume infinite callback tuning can make two independent top-level DWM
surfaces behave exactly like one native window.

After fixing the concrete duplicate work above, measure container drag/resize.

The current Shepherd architecture intentionally keeps guests as independent
top-level HWNDs. This is excellent for input/focus reversibility and avoids
SetParent/AttachThreadInput, but there is a compositor synchronization ceiling:
the WPF container and guest HWNDs are separate DWM surfaces.

Investigate an earlier movement signal such as WM_WINDOWPOSCHANGING, using the
proposed container rect to pre-position guest(s) before the container's move is
committed.

Do NOT blindly add another callback.

If WM_WINDOWPOSCHANGING materially improves jitter, use it as authoritative
during the native move loop and suppress later duplicate glue.

If consumer-grade drag still cannot be achieved, produce an architecture
decision with measured evidence comparing:

A. Shepherd top-level HWNDs (current)
B. reversible reparenting (likely reject because historical input/DPI risk)
C. DWM thumbnail / Windows Graphics Capture visual embedding + separate input
   forwarding (major complexity)
D. different shell/container strategy

Do not switch architectures without evidence and a migration plan.
