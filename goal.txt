# 3. NON-NEGOTIABLE ARCHITECTURAL INVARIANTS

Unless CURRENT source/spec explicitly supersedes them, preserve:

## Shepherd

- no production `SetParent`;
- no conversion of guests to child HWNDs;
- no guest style/exstyle/owner containment mutation;
- guests remain independent top-level windows.

## Geometry

- guest layout is based on physical screen pixels;
- do not casually introduce WPF DIP conversion into guest positioning;
- split panes must exactly partition their authoritative content rectangle.

## Z-order

- `WindowShepherdService` or current equivalent remains the authoritative positioning/z-order policy owner;
- no global `HWND_BOTTOM` repair;
- no competing independent z-order subsystems;
- correct geometry alone is NOT enough — local order must also be correct.

## Visibility

Normal:

    VisibleManagedGuests = {active member}

Split:

    VisibleManagedGuests = {left, right}

Container minimized:

    VisibleManagedGuests = {}

Popup/chrome interaction does NOT logically change the visible set.

## Split

Split remains active until:

- explicit unsplit;
- explicit pair replacement;
- structural removal of a pair member.

Unrelated hover/click must not implicitly destroy the pair.

## Crash safety

Journal-before-hide ordering must remain correct.

## HWND lookup

Preserve O(1) captured HWND/member lookup.

## WinEvents

Preserve the current direct-click `EVENT_OBJECT_REORDER` solution unless evidence proves it wrong.

## Movement

Do not regress recently improved live movement/resize smoothness.

# 5. FINDING SEVERITY MODEL

Classify every credible finding.

Use:

## CRITICAL

Examples:

- application or guest data loss;
- security boundary bypass;
- arbitrary destructive action;
- hidden guest unrecoverable after crash;
- severe corruption;
- runaway process spawning;
- catastrophic lifecycle failure.

## HIGH

Examples:

- reproducible app crash;
- window permanently lost/hidden;
- incorrect split/z-order lifecycle;
- persistence corruption;
- major race;
- cross-machine correctness failure.

## MEDIUM

Examples:

- non-destructive correctness defect;
- meaningful performance issue;
- resource leak;
- confusing lifecycle behavior;
- flaky critical automation;
- observability gap blocking diagnosis.

## LOW

Examples:

- minor inefficiency;
- dead code;
- maintainability problem;
- documentation drift;
- low-impact UX inconsistency.

Also record:

    CONFIRMED
    PROBABLE
    SPECULATIVE

# 66. FINAL PRINCIPLE

This audit exists to discover things we do NOT already know.

Do not spend the entire run merely proving the known feature works.

Attack assumptions.

Read uncomfortable code.

Trace weird lifecycle paths.

Construct adversarial event orderings.

Look for:

    "This is only safe if event X always arrives before Y."

    "This assumes the HWND cannot be recycled."

    "This assumes WPF layout has already completed."

    "This assumes the guest is foreground if visible."

    "This assumes disk writes succeed."

    "This assumes the test cleanup always runs."

    "This assumes only one monitor."

    "This assumes no callback arrives after disposal."

Those assumptions are where the most valuable findings will come from.

But every change still needs evidence.

The ideal end state is not:

> lots of code changed.

It is:

> the entire repository has been interrogated systematically, real defects have been fixed, fragile assumptions have been hardened, tests have become more meaningful, architecture has remained coherent, and the remaining risks are explicitly known.

Begin now with repository recovery and a full-system architecture map, then proceed through the audit phases until the production engineering gate is satisfied.
