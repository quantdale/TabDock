## 1. System map

**Stack:** C# 12 / .NET 8 (`net8.0-windows`) / WPF, P/Invoke-only (no NuGet dependencies), single `TabDock.csproj` plus an out-of-solution test harness (`tests/ValidationDriver/`) and an out-of-solution spike (`Spike/TabDock.Spike`, in `TabDock.sln` but excluded from the main csproj's globs).

**Entry point:** `App.xaml.cs` — constructs `LoggingService` → `IconService`/`WindowShepherdService`/`PersistenceService`/`GroupManager`/`WinEventMonitor`/`HotkeyService`, wires WinEvent handlers (`WireWinEvents`), restores persisted groups as empty shells, opens `MainWindow`, registers the global hotkey, starts the WinEvent hook.

**Core model:** `GroupManager` owns `ObservableCollection<Group>`; each `Group` owns `ObservableCollection<CapturedWindow>` (live) plus `List<PersistedTabMetadata>` (layout intent surviving reboots). `WindowShepherdService` is the only capture backend — a captured HWND is never reparented, only positioned/z-ordered/shown/hidden via `SetWindowPos`/`ShowWindow`, with placement restored via `WINDOWPLACEMENT` on release. `WinEventMonitor` is a single out-of-process `SetWinEventHook` wrapper covering `EVENT_OBJECT_DESTROY`, `EVENT_SYSTEM_FOREGROUND`, `EVENT_OBJECT_NAMECHANGE`, `EVENT_SYSTEM_MINIMIZESTART`, `EVENT_OBJECT_HIDE`, and the `MOVESIZESTART..MOVESIZEEND` range, all re-dispatched onto the UI thread via `SynchronizationContext.Post` (never `Send`) — that Post-not-Send choice is load-bearing per the comment at `Services/WinEventMonitor.cs:136-140`.

**Persistence:** `PersistenceService` does atomic-write (`.tmp` + `File.Move(overwrite:true)`) to `%APPDATA%\TabDock\state.json`; `WindowShepherdService` does the same pattern to a separate `%APPDATA%\TabDock\hidden-windows.json` crash-recovery journal (see ISSUE-01 below — this second file doesn't get the same debouncing the first one does).

**UI:** `MainWindow` (launcher) → `ContainerWindow` (one per group, hosts `NativeHwndHost` as a pure position marker, never a real host) → `CapturePickerWindow` (modal, `EnumWindows`-backed picker). View models: `MainViewModel` → `GroupViewModel` → `TabViewModel`; `CapturePickerViewModel` is independent (constructed fresh per picker invocation).

**Data/I/O edges:** `%APPDATA%\TabDock\state.json`, `%APPDATA%\TabDock\hidden-windows.json`, `%APPDATA%\TabDock\logs\TabDock.log` (rotated at 1 MB by `LoggingService`); `EnumWindows`/`SetWinEventHook`/`SendInput` as OS-level I/O edges; no network I/O anywhere in the main app.

### AUDIT25-01 — Hidden-window crash-recovery journal does synchronous file I/O on the UI thread on every tab switch, not just on hide

- Status: **CONFIRMED**
- Lens: C (Performance), F (Architecture — inconsistent with the sibling fix already applied to `state.json`)
- Location: `Services/WindowShepherdService.cs:128-174` (`PositionAndShow` → `JournalClear`, `Hide` → `JournalHide`), `Services/WindowShepherdService.cs:289-350` (`JournalHide`/`JournalClear`/`LoadJournal`/`SaveJournal`) — at commit `f9950990`.
- Evidence:
  - `PositionAndShow` (called every time a tab becomes active) calls `JournalClear(window.Hwnd)` synchronously (line 155).
  - `Hide` (called every time the previously-active tab is hidden — i.e. on every single tab switch, via `ContainerWindow.SyncShepherdActiveWindow`, `Views/ContainerWindow.xaml.cs:538-556`) calls `JournalHide(window)` synchronously (line 172).
  - `JournalHide`/`JournalClear` both call `LoadJournal()` (`File.ReadAllText` + JSON deserialize, or a `File.Exists` check) and, when the entry set changed, `SaveJournal()` (`JsonSerializer.Serialize` + `File.WriteAllText` to a `.tmp` file + `File.Move(overwrite:true)`) — three to four synchronous filesystem calls, back to back, on the WPF dispatcher thread.
  - Contrast with `GroupManager.RequestSave()` (`Services/GroupManager.cs:54-67`), whose own comment explicitly names this exact problem and debounces it: *"Debounced SaveState: persists layout intent ~1s after the most recent state change so it survives crashes and force-kills..., without a disk write per event for high-frequency mutations such as drag-reorder."* The journal writer in `WindowShepherdService` is the same class of high-frequency event (every tab switch, not just drag-reorder) but received no equivalent treatment.
- Problem: Every tab switch now costs 2 read-then-maybe-write file round trips on the UI thread (clear the incoming tab's entry, journal the outgoing tab's entry), synchronously inside the WM_ACTIVATE-adjacent code path that also does `SetWindowPos`/`ShowWindow`. On a slow, contended, or (common in managed/enterprise Windows environments) network-redirected `%APPDATA%` profile, this is a direct UI-thread stall on an interactive, latency-sensitive path — the exact failure mode `RequestSave`'s debounce was written to avoid one file over.
- Severity: **Medium**. Not data-loss or crash-level, but it's a real, easily-reproduced UI hitch under a plausible and common condition (roaming profile / slow disk), on the single most frequent user interaction in the app (tab switching).
- Impact: Perceived jank/stutter on tab switch; worse under I/O contention (e.g., antivirus scanning `%APPDATA%`, a redirected profile, a full SSD).
- Likelihood: Every single tab switch, unconditionally — the file I/O itself always runs; only its *duration* varies with disk conditions.
- Root cause: The crash-recovery journal was added to solve a real problem (rescuing a hidden guest after a force-kill) but reused the same eager "write on every state change" pattern as an earlier, un-debounced version of the metadata store, without carrying forward the debounce fix that the metadata store itself later needed.
- Recommendation: Debounce/batch the journal writer the same way `GroupManager.RequestSave` does — coalesce rapid `JournalHide`/`JournalClear` calls onto a short (e.g. 250-500ms) `DispatcherTimer` and write the accumulated in-memory journal state once. Since the journal's only consumer (`RescueOrphanedWindows`) runs once at next startup, a short debounce window does not weaken the crash-recovery guarantee in any way that matters (a crash within that window loses at most the very latest hide, which is no worse than the current window between "hide the guest" and "the async file write actually lands" that already exists today with `File.Move`'s own latency).
- Trade-offs & alternatives: (a) Move the I/O to a background `Task.Run` fire-and-forget with a lock around the file — removes the UI-thread block immediately but does more total I/O than debouncing; (b) keep the journal purely in-memory during the session and flush only periodically + on the already-existing `Application_Exit`/crash paths — cheapest, but a call site auditing pass would be needed to confirm every crash path still flushes before the process dies (some of `App.xaml.cs`'s crash handlers already call `_groups.SaveState()`, which could be extended to also flush the journal). Debouncing (the recommendation) is the smallest, lowest-risk change that mirrors an already-proven pattern in the same codebase.
- Complexity & risk: Quick win — same shape as the existing `RequestSave`, single file, no cross-cutting changes.
- Implementation steps: 1) Add a `DispatcherTimer`-based debounce in `WindowShepherdService`, mirroring `GroupManager.RequestSave`. 2) Change `JournalHide`/`JournalClear` to mutate an in-memory `HiddenWindowJournalFile` and call the debounce trigger instead of `SaveJournal` directly. 3) Ensure `Application_Exit`/dispatcher-crash paths in `App.xaml.cs` force an immediate flush (bypass the debounce) before shutdown, since a debounced write that never fires because the process died defeats the crash-recovery purpose entirely for that last window.
- Proposed change: not included as a diff — the exact debounce shape should match `GroupManager.RequestSave`'s existing style once implemented, and the flush-on-crash requirement (step 3) needs a decision on which exit paths to wire it to; recommend confirming that decision before writing the diff.
- Regression safety: Add/extend a ValidationDriver scenario that force-kills TabDock immediately after a rapid sequence of tab switches (no settle time) and verifies the last hidden guest is still rescued at next launch — this is the one behavior debouncing could plausibly regress if the crash-flush (step 3) is missed.
- Verification: N/A (confirmed by direct code read, not hypothesis).

### AUDIT25-02 — Capture-picker window enumeration extracts every visible window's icon synchronously, on the UI thread, on every open/refresh

- Status: **CONFIRMED**
- Lens: C (Performance)
- Location: `ViewModels/CapturePickerViewModel.cs:60-109` (`Refresh`), specifically line 99 (`Icon = _icons.GetWindowIcon(hwnd)`) inside the `EnumWindows` callback; `Services/IconService.cs:20-31` (`GetWindowIcon` → `GetProcessImagePath` + `GetFileIcon`), `Services/IconService.cs:33-67` (`GetFileIcon` → `ExtractIconEx` + `Imaging.CreateBitmapSourceFromHIcon`).
- Evidence: `Refresh()` runs `NativeMethods.EnumWindows` synchronously; for every surviving candidate window (visible, not cloaked, not a tool window, has a title, not TabDock's own) it calls `_icons.GetWindowIcon(hwnd)` inline, which in turn calls `OpenProcess`/`QueryFullProcessImageName` and then `ExtractIconEx` (a `shell32.dll` call that reads the icon resource out of the target `.exe` from disk) and `Imaging.CreateBitmapSourceFromHIcon` (GDI→WPF bitmap conversion) — all before the `EnumWindows` callback returns `true` to continue enumeration. This is called every time `CapturePickerViewModel` is constructed (i.e., every time `Ctrl+Alt+G` is pressed or "+ " is clicked, per `App.xaml.cs:428-436`) and every time `RefreshCommand` fires.
- Problem: A typical desktop session easily has 10-30+ qualifying top-level windows. Each one costs a process handle open, a `QueryFullProcessImageName` call, and a synchronous disk read to extract its icon — done serially, on the UI thread, before the picker dialog can render its list. This is the classic N+1-style synchronous-I/O-in-a-loop pattern, on the most latency-sensitive user-facing surface in the app (a modal dialog the user just explicitly asked to open).
- Severity: **Low-Medium**. Doesn't corrupt state or crash; degrades perceived responsiveness of the picker's open animation/first paint in proportion to open-window count. Likely tolerable at typical window counts (a handful) but noticeable for power users with many windows open (the exact audience most likely to want a window-tabbing tool in the first place).
- Impact: Slower `Ctrl+Alt+G` → dialog-visible latency; worsens linearly with open-window count.
- Likelihood: Every picker open, unconditionally.
- Root cause: Icon loading was written as part of the enumeration loop for simplicity, with no separation between "enumerate + populate the list" and "decorate with icons."
- Recommendation: Populate `Windows` first without icons (fast, all in-memory `user32` calls), show the dialog, then load icons asynchronously per-item (e.g., `Task.Run` per window or a small bounded-concurrency batch) and set `WindowInfo.Icon` on the UI thread as each one completes — `WindowInfo` already implements `INotifyPropertyChanged` via `ViewModelBase`, so the UI updates incrementally with no XAML change needed.
- Trade-offs & alternatives: A simpler mitigation is an icon cache keyed by `ExePath` (most "top-level windows" on a desktop are multiple windows of the same few apps — browser, terminal, IDE — so an exe-path cache would cut redundant `ExtractIconEx` calls without any async restructuring). This is a smaller, lower-risk fix than full async loading and could be done first as a quick win, with async loading as a follow-up for the cold-cache case.
- Complexity & risk: Quick win (exe-path cache) to Medium (async icon population); low regression risk either way since icons are cosmetic — worst case on a bug is a blank/default icon, not incorrect capture behavior.
- Implementation steps (cache-first option): 1) Add a `static Dictionary<string, ImageSource>` (or instance-level, scoped to `IconService`'s lifetime) keyed by exe path in `IconService`. 2) Check the cache before calling `ExtractIconEx` in `GetFileIcon`. 3) For the async option, additionally split `Refresh()` into a synchronous list-population pass and a fire-and-forget per-item icon-fetch pass.
- Regression safety: Manually verify the picker still shows the correct icon per window after the change (existing manual checklist in README.md already exercises the picker); no automated coverage currently targets picker icon correctness specifically.
- Verification: N/A (confirmed by direct code read).

### AUDIT25-03 — Stale doc comment in `WinEventMonitor` describes the deleted Reparent architecture, not Shepherd

- Status: **CONFIRMED**
- Lens: M (Documentation drift), with elevated importance because this is exactly the file/area CLAUDE.md tells agents to be careful in
- Location: `Services/WinEventMonitor.cs:125-129`.
- Evidence: The comment reads: *"Do NOT resolve GetAncestor(GA_ROOT) here: a captured window is a WS_CHILD of the TabDock container (its root is our own window, which the old filter rejected), and a window that just fired EVENT_OBJECT_DESTROY has no ancestors to walk at all."* This directly contradicts the Shepherd model's core invariant, stated in the same codebase in at least three other places: `CLAUDE.md` ("A captured guest is *never* reparented or restyled... it stays a real, independent top-level window"), `AGENTS.md` ("A captured window is never reparented"), and `Services/WindowShepherdService.cs`'s own class-level doc comment ("no SetParent, no style/ex-style mutation..."). Under Shepherd, a captured window is **not** `WS_CHILD` of anything TabDock owns — it remains its own top-level window, so `GetAncestor(GA_ROOT)` on it returns itself (or its own owner chain), never the TabDock container.
- Problem: The comment's *conclusion* ("don't use `GetAncestor(GA_ROOT)` here, use direct HWND match instead") is still correct — the code itself (`_isCapturedWindow(hwnd)` direct match, line 130) is right and the real reason (a destroyed window has no ancestors to walk, so `GetAncestor` would silently drop the destroy event) is *also* stated correctly in the same comment and in `CLAUDE.md`'s "Its filter is a direct captured-member HWND match... do not reintroduce `GetAncestor(GA_ROOT)`" guidance. But the *stated premise* ("a captured window is a WS_CHILD of the TabDock container") is simply false post-migration, and this is precisely the kind of comment a future agent or engineer reads first when touching WinEvent/z-order code — CLAUDE.md explicitly names this file's filter as sensitive and history-laden. A reader who trusts this specific sentence could reintroduce reparent-era assumptions elsewhere.
- Severity: **Low** (no runtime effect — the code is correct), but flagged because of where it sits: exactly the file CLAUDE.md calls out as "do not reintroduce X here," and the comment giving the wrong reason for the right rule undermines the reliability of that warning for the next reader.
- Impact: Risk is entirely to future maintainers'/agents' mental model, not to running behavior.
- Likelihood: Triggers only when someone reads this comment while modifying WinEvent filtering logic — plausible given CLAUDE.md points agents at exactly this area before z-order/activation work.
- Root cause: Leftover from the pre-Shepherd (Reparent) backend; not updated when the Shepherd migration (`docs/internal/deep-audit-2026-07-17.md`) deleted the WS_CHILD relationship this comment describes.
- Recommendation: Update the comment to state the Shepherd-era reason: a captured window is never reparented, so `GetAncestor(GA_ROOT)` on a live captured window returns itself (not a TabDock ancestor) and is useless for "is this ours" filtering regardless of the destroyed-window edge case; the direct-HWND-match filter is required for both reasons (correct semantics *and* survives destroy events).
- Trade-offs & alternatives: None — this is a comment-only fix.
- Complexity & risk: Quick win, zero behavioral risk (comment-only change).
- Implementation steps: Rewrite `Services/WinEventMonitor.cs:125-129`'s comment to match current architecture.
- Proposed change:
  ```csharp
  // Every consumer of these events reacts only to captured member windows,
  // so filter by direct HWND match. Do NOT resolve GetAncestor(GA_ROOT) here:
  // under the Shepherd model a captured window is never reparented, so it is
  // its own root already (GetAncestor would just return the window itself,
  // never a TabDock container, making it useless as an ownership filter) —
  // and a window that just fired EVENT_OBJECT_DESTROY has no ancestors to
  // walk at all regardless.
  ```
- Regression safety: None needed beyond a doc review; no code path changes.
- Verification: N/A (confirmed by direct comparison of this comment against CLAUDE.md/AGENTS.md/WindowShepherdService.cs, all read this session).

### AUDIT25-04 — `NuGetAudit` disabled at the project level, not scoped to the stated reason

- Status: **CONFIRMED** (the setting), **HYPOTHESIS** (whether it currently matters)
- Lens: I (Dependencies/supply chain), J (Build hygiene)
- Location: `TabDock.csproj:12-13`.
- Evidence: `<NuGetAudit>false</NuGetAudit>` with the comment *"The build environment cannot reach nuget.org for vulnerability audit data; disable it so the build is warning-free."*
- Problem: This is a blanket, permanent suppression of `dotnet`'s built-in NuGet vulnerability audit, justified by a build-*environment* constraint (no network access) rather than scoped to it (e.g., via a build-time property override only in that constrained environment). Today's impact is genuinely low — `AGENTS.md`/`CLAUDE.md` both state the project has zero third-party NuGet package references, so there is nothing for the audit to currently flag. But the setting is committed into the project file itself, so it silently persists as a standing policy the moment any dependency is ever added, in *any* environment, including ones with network access.
- Severity: **Low** today (no dependencies to audit); would become **Medium-High** the day a dependency is added, since the suppression would then hide real CVE data with no visible warning that it's off.
- Impact: None currently observable; latent risk is entirely forward-looking.
- Likelihood: Only matters if/when a NuGet dependency is ever introduced.
- Root cause: A local build-environment limitation was solved by a global, permanent project setting instead of a locally-scoped override (e.g., an environment variable or a `Directory.Build.props` override used only by the constrained build environment).
- Recommendation: Either (a) move the suppression to whatever CI/local build config is actually network-constrained (leaving the checked-in `.csproj` audit-enabled by default), or (b) if it must stay in the `.csproj`, add a standing reminder (e.g., in `AGENTS.md`'s "Development conventions" or a comment right at the setting) that says "re-verify this is still needed and re-run an audit out-of-band before adding any dependency, and before every release," so the suppression can't silently outlive its own justification.
- Trade-offs & alternatives: Leaving as-is is low-risk *only* for as long as the zero-dependency policy holds; the recommendation costs nothing and removes a footgun for whoever adds the first dependency.
- Complexity & risk: Quick win, zero behavioral risk.
- Implementation steps: Add the reminder comment (cheapest option) or relocate the suppression to a build-environment-specific override.
- Regression safety: N/A.
- Verification: Confirm whether the actual CI/release process (not visible in this repo — no CI config was found under a quick top-level scan) has network access; if it does, the audit could simply be re-enabled there with no downside today.

### AUDIT25-05 — `ContainerWindow.WndProc`'s WM_ACTIVATE handler creates an uncancelled `DispatcherTimer` on every activation

- Status: **CONFIRMED**
- Lens: D (Concurrency/async — timer lifecycle), G (Code quality)
- Location: `Views/ContainerWindow.xaml.cs:142-164`.
- Evidence: Every `WM_ACTIVATE` with `WA_ACTIVE`/`WA_CLICKACTIVE` and a non-null `_shepherdActiveWindow` allocates a brand-new `DispatcherTimer` (120ms) with a closure capturing the current `activeWindow` snapshot, and starts it — with no reference kept to cancel a still-pending prior timer if activation happens again within that 120ms window (e.g., rapid alt-tab flicker, or clicking the title bar twice quickly).
- Problem: Each timer that fires re-checks `_shepherdActiveWindow == activeWindow && IsWindowVisible(...)` before calling `BringToFront`, so a stale timer for the *same* still-active window is merely redundant work (an extra `SetWindowPos`/possibly `SetForegroundWindow` call), not incorrect — but it is unbounded: N activations within 120ms of each other queue N timers, all of which fire and all of which call into `WindowShepherdService.BringToFront`. `BringToFront` itself is written defensively (early-returns if already foreground), so the practical failure mode is wasted CPU/native calls under rapid activation churn, not a visible bug.
- Severity: **Low**. No observed correctness impact given `BringToFront`'s existing defensiveness; flagged as a code-quality/resource-discipline gap, not a functional defect.
- Impact: Minor wasted work under rapid-activation-churn conditions (unlikely to be user-visible).
- Likelihood: Requires activation events firing faster than 120ms apart — an edge case, not a common interaction pattern.
- Root cause: Same throwaway-timer-per-event pattern is used at `ContainerWindow_StateChanged` (`Views/ContainerWindow.xaml.cs:313-319`) too, without a single shared "debounce/coalesce the last pending action" helper.
- Recommendation: If addressed, keep a single field for the pending timer and `Stop()`/replace it rather than allocating a new one each activation (the same coalescing pattern already used correctly for `RequestSave` in `GroupManager` and `DebounceNameChanged` in `App.xaml.cs`). Given the Low severity and lack of observed impact, this is optional polish rather than a must-fix.
- Trade-offs & alternatives: Leave as-is; the existing `BringToFront` defensiveness already bounds the damage.
- Complexity & risk: Quick win if pursued; purely local, no cross-cutting risk.
- Implementation steps: Add a `DispatcherTimer?` field, `Stop()` any existing instance before creating a new one, mirroring `App.xaml.cs`'s `DebounceNameChanged`.
- Regression safety: Manual re-test of alt-tab / rapid-click activation scenarios already in the README checklist.
- Verification: N/A (confirmed by direct code read); the "how often does this actually fire twice within 120ms in practice" question is a HYPOTHESIS that would need a runtime trace to quantify, but doesn't change the recommendation either way given `BringToFront`'s existing guard.
