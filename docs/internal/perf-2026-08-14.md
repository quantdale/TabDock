# TabDock performance optimization campaign — 2026-08-14

## Scope and baseline

This campaign used the live Git baseline, not the SHA in the request as an
assumption. At startup, `main`, `HEAD`, and `origin/main` all resolved to
`e0cde3405d7c2434baff3583439c1d5cb661d76a`, and the working tree was clean.
The prior review is documented in `docs/internal/perf-2026-07-25.md` and its
runtime optimizations were preserved.

Measurements were collected on Windows 10 build `10.0.26200`, .NET
`8.0.30`, `win-x64`, 12 logical processors, workstation GC, Release
configuration. The harness is non-gating and writes ignored JSON reports via
`scripts/perf.ps1`; it uses production `DiagnosticTrace`, `LoggingService`,
`CapturePickerViewModel`, `IconService`, and `PersistenceService` paths.

## Retained changes

### OPT-01 — early desktop reorder filtering

1. Original cost: every desktop-source `EVENT_OBJECT_REORDER` could snapshot
   foreground state, allocate diagnostic metadata, and post to the dispatcher
   before the later membership check rejected unrelated desktop activity.
2. Invariant: the desktop hook remains installed as the z-order signal; a
   captured callback preserves the callback-time `CapturedWindow` reference,
   dispatcher hop, and dispatch-time reference/HWND validation.
3. Change: resolve the callback-time foreground HWND through the captured
   member index and return before diagnostics/posting when it is uncaptured.
4. Safety: numeric HWND presence alone is not used; the normal resolver and
   later `ReferenceEquals` check remain in place, including recycled-HWND and
   release races.
5. Measurement: the harness and self-test cover the production trace/logger
   paths; the deterministic self-test proves uncaptured drop, captured post,
   release rejection, recycle rejection, successful dispatch, and preserved
   callback/dispatch trace events.
6. Validation: `WinEventMonitorSelfTest.DesktopReorderDropsUncapturedAndRejectsStaleDispatch`.

### OPT-02 — one diagnostic metadata allocation

1. Original cost: `DiagnosticEventRecord` constructed an empty `Data`
   dictionary and `DiagnosticTrace.Record` replaced it with a second empty or
   defensive-copy dictionary. Snapshot cloning repeated the same pattern.
2. Invariant: `Data` remains a non-null public dictionary; caller metadata and
   snapshot metadata remain isolated; ordering, sequence numbers, capacity,
   clearing, and concurrency are unchanged.
3. Change: route both construction and cloning through an internal constructor
   that creates exactly one dictionary.
4. Safety: supplied metadata is still copied with the ordinal comparer; no
   caller-owned dictionary is retained.
5. Measurement: no-data `DiagnosticTrace.Record` allocation fell from
   `3,440,040` to `2,640,040` bytes per 10,000 events (about 23.3%); the
   100,000-event case fell from `34,400,072` to `26,400,056` bytes. Metadata
   input fell from `6,960,040` to `6,160,040` bytes per 10,000 events. The
   timestamp string representation was not changed because the campaign did
   not need the contract risk.
6. Validation: diagnostic defensive-copy, deep-snapshot, clear, capacity,
   sequence, and concurrent-recording self-tests; final result `193 checks / 0
   failures`.

### OPT-03 — cached post-Loaded container HWND

1. Original cost: several post-Loaded `ContainerWindow` paths repeatedly asked
   WPF for `new WindowInteropHelper(this).Handle` even though the Loaded-time
   `_containerHwnd` safety cache already existed.
2. Invariant: the pre-Loaded `OnSourceInitialized` query and zero-handle guards
   remain; teardown does not query a late WPF handle.
3. Change: use `_containerHwnd` only in paths proven to run after Loaded.
4. Safety: `OnSourceInitialized` and `EnsureHandle` retain their original
   lifecycle behavior; all changed paths still reject zero handles.
5. Measurement: this is a small allocation/work elimination; no separate
   stopwatch claim is made.
6. Validation: final Release build, geometry/diagnostic self-tests, and
   published executable smoke passed.

### OPT-04 — bounded background picker icon resolution

1. Original cost: cold `Refresh()` synchronously performed icon extraction for
   every candidate. The pre-change picker baseline (six candidates on the
   measured desktop) was approximately 3.7–4.0 ms median with cold tails from
   44–115 ms across the captured baseline runs; warm refresh was approximately
   0.5–0.7 ms median.
2. Invariant: candidate filters, order, executable-path reuse, icon cache
   lifetime/null-failure caching, frozen `ImageSource` values, selection, and
   destination-group behavior remain unchanged.
3. Change: add rows after enumeration immediately, apply completed cache hits
   on the UI path, and resolve misses on exactly one bounded worker. A refresh
   generation and row identity gate prevent stale results from updating a new
   refresh. `IconService` uses a locked cache plus per-path single-flight so
   simultaneous callers do not duplicate native extraction. Picker close and
   refresh cancel/invalidate work safely.
4. Safety: no HWND identity or capture filter moved to the worker; only cosmetic
   frozen image assignment is asynchronous. Worker cancellation has atomic
   `CancellationTokenSource` ownership, and dispatcher updates re-check
   disposal, generation, and row membership.
5. Measurement: three final quiet runs with 7 samples each measured:

   | Metric | Final median range | Final p95 range |
   | --- | ---: | ---: |
   | cold rows available (`Refresh`) | 1.49–1.77 ms | 34.18–44.52 ms |
   | cold icon completion | 4.04–17.23 ms | 59.28–65.21 ms |
   | warm rows available (`Refresh`) | 1.34–1.61 ms | 1.84–6.49 ms |
   | warm icon completion | about 0.001 ms | 0.07–0.11 ms |

   Candidate counts were 4–5 and enumerated desktop windows were 936–939 in
   those runs. The key user-visible result is that rows no longer wait for the
   cold icon operation; warm completion remains effectively free. One matrix
   run under simultaneous build/npm/publish load had wider tails, so it is
   retained as variance evidence rather than a performance claim.
6. Validation: `CapturePickerSelfTest.BackgroundIconResolutionIsGenerationSafe`
   covers prompt rows, same-executable caching, stale refresh suppression,
   picker disposal, and extraction failure. OpenSpec adds the generation,
   bounded-worker, and close-safety scenarios.

## Build, CI, and reproducibility changes

### OPT-05 — no duplicate solution-contained builds

`TabDock.sln` already contains the main app and Spike. `scripts/validate.ps1`
now builds the solution once, then builds only the ValidationDriver and GuineaPig
projects that are outside the solution. The full intended Release projects,
self-tests, support/recovery smoke tests, OpenSpec validation, and publish all
remain in the flow. The matrix measured the removed explicit app and Spike
builds at about 2.07 s and 2.24 s respectively on one warm run, in addition to
the 2.47 s solution build; these are timing probes, not a CI threshold.

### OPT-06 — locked OpenSpec and NuGet tooling

- `tools/openspec/package.json` pins `@fission-ai/openspec` exactly at
  `1.8.0`; its committed lock file is installed with `npm ci --ignore-scripts`.
- GitHub Actions uses `setup-node` npm caching keyed by that lock file and no
  longer depends on a global CLI installation.
- `OPENSPEC_NO_UPDATE_CHECK=1` and `OPENSPEC_TELEMETRY=0` remain set.
- NuGet lock mode was evaluated locally, but it was not retained. Hosted CI
  resolved the SDK-generated `Microsoft.NET.ILLink.Tasks` dependency as
  `8.0.29` while the local lock file recorded `8.0.30`, producing `NU1004` in
  locked restore. Pinning that SDK-generated implementation detail would make
  the supported SDK/RID flow more fragile, so ordinary audited restore remains
  the reproducible project contract.
- Unlocked audited restore, Release builds, RID-specific publish, vulnerability
  audit, and OpenSpec validation passed. The OpenSpec matrix measured 57.66 s for a
  clean `npm ci` and 18.50 s for validation; the install is intentionally not
  repeated by normal local validation when the repository tool is already
  present.

## Investigated and intentionally unchanged

### OPT-08 — hot `SHEPHERD[position]` logging

The production logger was exercised with 10,000 real `LoggingService.Log`
calls using the position-line shape. The original baseline was 9.12 ms median,
35.18 ms p95, and 3,220,352 allocated bytes. Final quiet runs varied from
27.06–55.98 ms median and 63.34–207.15 ms p95 under desktop load; each clean
run wrote all 10,000 lines with no drop marker. A matrix run during heavy
publish/npm activity dropped lines, demonstrating why the bounded queue remains
important. The variation is environmental and does not establish a repeatable
caller-side win. Failure, recovery, and final geometry logs were therefore not
rate-limited or suppressed.

### OPT-09 — persistence transaction

Changed 3-group/4-tab durable saves measured 2.94–3.66 ms median in the final
quiet runs, with variable tails; unchanged saves measured 0.12–0.14 ms median.
The unchanged byte-identical skip remains effective. The existing flush/temp /
atomic-replacement plus backup transaction was retained: no alternate replace
primitive was introduced without a demonstrated durability and backup
advantage, and no semantic save was moved to asynchronous persistence.

### OPT-10 — minimum-track timer

Source and existing tests confirm that the five-second timer marks constraints
dirty, clears refusal state, and lets the next existing coalesced
`RequestRelayout()` reprobe. It does not itself start a second layout loop. No
extra timer-triggered relayout was added because the bounded retry semantics are
intentional and the current flow avoids resize wars.

### OPT-11 — z-order verification

The `GW_HWNDPREV`/pairing scan remains a defensive correctness check for the
Shepherd invariant. The code already skips geometry writes when the observed
rect is unchanged, limits z-order repair to unhealthy pairings, and retains
explicit reconciliation after move/resize and chrome transitions. No reliable
repeatable native-call benefit was established that justified a dirty-epoch
cache with additional invalidation obligations, so the scan was left intact.

### OPT-12 — large-class extraction

`ContainerWindow` and `WindowShepherdService` were characterized. The remaining
stateful paths combine HWND identity, recovery durability, visibility, z-order,
split presentation, and dispatcher sequencing. Extracting them would increase
cross-object state transitions. No pure policy extraction had a sufficiently
clear ownership boundary during this pass; no speculative refactor was kept.

## Coverage limits and validation

The deterministic harness covers trace, logger, picker, persistence, environment
fingerprint, and build/tool timings. Real-input tab-switch/drag scenarios remain
supervised ValidationDriver work because they send native input to the active
desktop; they were not run unattended in this campaign. The canonical final
command was run from the final tree:

```powershell
.\scripts\validate.ps1 -Configuration Release -Ci -Publish
```

It passed locked audited restore, solution/driver/GuineaPig Release builds,
geometry and `193 checks / 0 failures` diagnostics self-tests, version/doctor,
pending-recovery and redirected recovery smoke, support-bundle privacy,
OpenSpec `18 passed / 0 failed`, single-file publish, and published `--version`.

No performance threshold was made gating. The campaign retained only changes
with a direct safety argument and measurable eliminated work or user-visible
picker latency; it did not alter Shepherd/no-reparent behavior, HWND identity
checks, recovery journaling, persistence durability, min-track safety, z-order
verification, or packaging policy.
