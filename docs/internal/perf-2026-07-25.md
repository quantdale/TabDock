# TabDock Performance Pass — 2026-07-25

**Base commit:** `2b76d84` (branch `main`), implemented on `claude/system-performance-optimizations-am406n`.

This is a change record, not an audit: each item below was implemented in the same pass that identified it. Findings are numbered `PERF25-NN` to keep them distinct from the `AUDIT25-NN` series in `audit-2026-07-25.md` and the `M`/`H`/`L`/`RC` series in `investigation_findings.md`.

**Not measured.** No build or profiler run was possible in the session that produced this pass (no Windows toolchain available), so every "cost" below is derived from a direct code read — call counts, syscalls and allocations per event — never from a stopwatch. The numbers that would turn these into measurements are listed in §3.

**Scope discipline.** Every change is a like-for-like substitution: same observable behavior, less work per unit of it. Nothing here alters the Shepherd invariants (no reparenting, no style mutation, symmetric release), the crash-recovery journal's guarantees, the no-nesting rule, or any emergency-release path.

## 1. Changes

### PERF25-01 — `LoggingService` did a full open/write/close plus two stat calls per log line

- Location: `Services/LoggingService.cs`
- Before: the writer thread called `File.Exists(_logFile)` + `new FileInfo(_logFile).Length` (rotation check) and then `File.AppendAllText(...)` — an open, seek to end, write, and close — **for every single line**. The queue and background thread already kept callers off the disk, but the disk work itself was shaped as if lines were rare.
- Why it matters: lines are not rare. Dragging a container logs one `SHEPHERD[position]` line per mouse tick; a tab switch logs several; WinEvent handling logs per event. At ~100 lines/second that is ~300 filesystem operations per second, and `%APPDATA%` is commonly redirected to a network share in managed Windows environments (the same condition AUDIT25-01 called out).
- After: one append-mode `FileStream` + `StreamWriter` held open for the process lifetime; the writer takes the blocking first line, then drains up to 255 more with non-blocking `TryTake`, writes them as one `StringBuilder`, and flushes once. Rotation reads `FileStream.Position` (already tracked in memory, exact right after the flush) instead of re-stat'ing the file, and closes/moves/reopens only when it actually trips.
- Behavior preserved: same file, same UTF-8-without-BOM encoding, same 1 MB rotation to `TabDock.log.old`, same `TabDock.log.err` fallback, same drop-counting when the queue overflows. A quiet logger still writes and flushes each line immediately — batching only engages when lines are already queued, so durability against a force-kill is unchanged in exactly the case where a single line matters.
- Compatibility note: the file is opened with `FileShare.ReadWrite`, so readers that share properly still work while TabDock holds it open — `tests/ValidationDriver/TabDockLog.cs` (`FileShare.ReadWrite | FileShare.Delete`) and PowerShell's `Get-Content` both do. A reader that demands exclusive-ish sharing (a bare `File.ReadAllText`, which requests `FileShare.Read`) will now get a sharing violation while TabDock is running; use the share flags the ValidationDriver uses.

### PERF25-02 — Every desktop-wide WinEvent cost an O(groups × members) scan, twice

- Location: `Services/GroupManager.cs` (new index), `App.xaml.cs` (all six handlers)
- Before: `WinEventMonitor.OnWinEvent` called `GroupManager.IsCapturedWindow`, a nested loop over `Groups` × `Members`, for **every** hooked event on the desktop — `EVENT_OBJECT_DESTROY` and `EVENT_OBJECT_NAMECHANGE` alone fire for menus, tooltips and transient UI in every running process. Each App handler that then ran repeated the same search with `_groups.Groups.ToList()` (a fresh list allocation per event) plus a `FirstOrDefault` closure per group.
- After: `GroupManager` maintains a `Dictionary<IntPtr, CapturedMember>` mirroring every group's `Members`, and exposes `TryGetCapturedMember(hwnd, out group, out member)`. The filter and all six handlers are now one dictionary probe with no allocation.
- Why the index is maintained from `CollectionChanged` rather than from the capture/release call sites: members are added through `GroupViewModel` and removed through several distinct release paths (tab release, pop-out, drag-out, destroy, tray-hide, group close). Hooking the collections makes it structurally impossible for the index to drift from `Group.Members` — no future call site has to remember it exists.
- Behavior preserved: an HWND can only be a member of one group (enforced by the picker's filter and by `ContainerWindow.CaptureWindow`), so a single lookup returns exactly what the scan-every-group loops returned. The `ToList()` snapshots existed to survive a handler mutating `Groups` mid-iteration (a drag-out of the last tab closes its container and removes the group synchronously); a lookup never iterates `Groups`, so that hazard is removed rather than merely guarded.

### PERF25-03 — The desktop-wide hooks ran even with nothing captured

- Location: `App.xaml.cs` (`SyncWinEventMonitor`), `Services/GroupManager.cs` (`IsMonitoringNeeded` / `MonitoringNeededChanged`), `Services/WinEventMonitor.cs` (`Start`/`Stop` made restartable)
- Before: the six `SetWinEventHook` registrations were installed once at startup and held for the process lifetime. With no captured windows — the state TabDock sits in whenever the user is just running the launcher, and the state *every* restored group starts in, since HWNDs are never re-attached across reboots — every hooked event on the desktop was still marshalled into TabDock's message loop purely to be discarded by the captured-member filter.
- After: hooks are installed when the captured-window count crosses zero-to-one and removed when it returns to zero.
- Ordering: installation is immediate, driven off the member being added to its group, which happens before the guest is positioned and shown — there is no window in which an event could be missed. Removal is deferred one dispatcher turn, because the transition to zero is usually reached from inside a WinEvent handler (a guest was destroyed or hid itself), and it re-checks on arrival so releasing one window and capturing another in the same turn does not tear the hooks back down.
- `UnhookWinEvent` must run on the thread that installed the hooks; both callers are on the UI thread (startup, and the presence notification raised off the UI-thread-only group collections).

### PERF25-04 — Capture-picker enumeration ran its most expensive filters first

- Location: `ViewModels/CapturePickerViewModel.cs`
- Before: for every top-level window on the desktop the enumeration ran `IsOwnWindow` (a lock plus two P/Invokes), the captured-member check, and a `DwmGetWindowAttribute(DWMWA_CLOAKED)` cross-process query **before** the two cheap reads (`WS_EX_TOOLWINDOW`, window title) that reject the overwhelming majority of them. It then resolved the window's executable path twice: once explicitly, and again inside `GetWindowIcon`, which re-derived the PID and re-ran `OpenProcess` + `QueryFullProcessImageName`.
- After: filters are ordered cheapest-first (visible → tool-window style → has a title → not ours → not already captured → not cloaked), and the icon is resolved from the executable path already in hand via `GetFileIcon`.
- Behavior preserved: every filter is independent of the others, so only the order in which they reject changes — the same set of windows is offered. `IsOwnWindow` additionally checks this process's ID (cached once in `NativeMethods.CurrentProcessId`) before the ancestor walk, since every container HWND is in this process anyway.

### PERF25-05 — Icon cache missed on path casing

- Location: `Services/IconService.cs`
- The AUDIT25-02 exe-path cache used the default ordinal comparer. `QueryFullProcessImageName` can report the same executable with different casing for different processes, which re-ran `ExtractIconEx` and the GDI→WPF bitmap conversion for a path already cached. Now keyed with `StringComparer.OrdinalIgnoreCase` (Windows paths are case-insensitive). An empty path short-circuits to `null` instead of caching a failure under an empty key.

### PERF25-06 — `AccentBrush` allocated a converter and a brush per binding read

- Location: `ViewModels/GroupViewModel.cs`
- `ContainerWindow` binds `AccentBrush` from several places, and WPF re-reads the property for each binding on every change notification; the getter constructed a fresh `ColorToBrushConverter` and a fresh `SolidColorBrush` every time. Now a single static converter and a cached frozen brush, rebuilt only when the colour string actually changes. A frozen brush is safe to share across bindings.

### PERF25-07 — Redundant work on the two remaining per-event paths

- `Services/WindowShepherdService.cs`: `PositionAndShow`'s log line no longer calls `DescribeWindow` (five extra P/Invokes to report a rect the line already carries — and the pre-move one at that). This runs on every `LocationChanged`/`SizeChanged` tick of a container drag. The line itself is unchanged in prefix and still emitted per position, which the `instant-tabswitch` ValidationDriver scenario asserts on. `JournalClear` returns before `RemoveAll` when the journal is empty (the normal case), so the drag path allocates no predicate closure.
- `Views/ContainerWindow.xaml.cs`: `LayoutShepherdActiveWindow` calls `UpdateLayout()` when layout is dirty (`!IsMeasureValid || !IsArrangeValid`). **Correction (2026-08-03):** the original unconditional flush (commit `2e42942`) and this file's own correction to a conditional-only flush were both wrong for maximize/restore — at `StateChanged` time this Window's own `IsArrangeValid` is still true for the old size (the native-resize invalidation has not propagated yet), so `UpdateLayout()` is a no-op and the guest is left at the pre-transition size even when forced. The marker's native HWND is only actually resized by the WPF layout pass that runs afterwards, and `HwndHost` does not re-raise its own `SizeChanged` for that pass. The guest is now re-glued from the window's `LayoutUpdated` event, which fires after every completed layout pass — by then the marker really has its new size. To keep that cheap, `LayoutShepherdActiveWindow` short-circuits before the P/Invokes when the guest already exactly covers the target rect (1px epsilon) and is visible: tab-strip reorders fire `LayoutUpdated` without moving the content marker, and re-issuing `PositionAndShow` mid-gesture would churn the guest/container z-order. A pure container move dirties no layout and raises no `LayoutUpdated`, so the per-tick drag path (`LocationChanged`) keeps the cheap guarded form.
- `Views/ContainerWindow.xaml.cs` + `App.xaml.cs`: a guest rename now refreshes only its own tab (`RefreshTabTitle`) instead of invalidating every tab's `Title` binding, and `HandleNameChanged` returns early when the "new" title equals the one already stored — some guests re-announce an unchanged caption repeatedly.
- `Services/PersistenceService.cs`: `Save` skips the write + atomic rename when the serialized JSON is byte-identical to what it last wrote (and `state.json` is still on disk, so a file deleted underneath a running TabDock is still recreated). Saves are debounced onto every state change and then repeated outright by the exit/crash paths, so identical writes were common.

## 2. Deliberately not done

- **Async icon loading in the picker** (AUDIT25-02's follow-up option). PERF25-04/05 remove the duplicate process query and the casing misses; full async population is a larger restructuring whose value should be judged against a measurement first.
- **Reusing the three `DispatcherTimer` instances in `ContainerWindow`** (WM_ACTIVATE re-assert, settled-state snapshot, self-minimize restore). Allocating a timer per occurrence is small next to the P/Invokes each one exists to schedule, and this is code with a documented history of subtle timing bugs (AUDIT25-05, finding #3). Not worth the risk for the saving.
- **Reducing the hooked event set.** `EVENT_OBJECT_DESTROY`/`NAMECHANGE` are the noisiest but each has a consumer that needs desktop-wide scope. PERF25-03 addresses the idle case instead, which is where the waste actually was.
- **Any `TabDock.csproj` change.** ReadyToRun is already on and Native AOT remains incompatible with WPF; nothing else offered a defensible win.

## 3. What would turn this into a measurement

- **PERF25-01**: wall-clock of `WriterLoop` per 1000 lines, before/after, with `%APPDATA%` on a local SSD and on a redirected network share.
- **PERF25-02/03**: TabDock's CPU time over a fixed 60-second desktop workload (open/close menus in other apps, switch windows) with zero groups captured, before/after.
- **PERF25-04**: `Stopwatch` around `Refresh()`'s `EnumWindows` call at a realistic window count (10-30) — the same measurement AUDIT25-02 left open.
- **PERF25-07**: frame timing while dragging a container with one docked guest; the `instant-tabswitch` scenario already asserts click-to-docked under 400 ms and is the closest existing automated proxy.
