# Deep Read-Only Whole-Codebase Audit

You are performing a **deep, exhaustive, repository-wide technical audit** of this codebase.

Your role is **NOT to implement, refactor, fix, format, clean up, migrate, or otherwise modify the software**.

Your job is to **read, inspect, reason about, cross-reference, test where safely possible, and document findings**.

The final deliverable is a **single Markdown audit report** containing all findings.

---

# 1. NON-NEGOTIABLE OPERATING CONSTRAINTS

## READ-ONLY CODEBASE

Treat the entire repository as **strictly read-only**.

You MAY:

* Read files.
* Search files.
* Search symbols/references.
* Inspect Git history.
* Inspect branches/tags if useful.
* Inspect configuration.
* Inspect dependency manifests and lockfiles.
* Inspect CI/CD definitions.
* Inspect tests.
* Inspect generated metadata.
* Run non-destructive diagnostic commands.
* Run existing tests, linters, type-checkers, builds, static analyzers, or other validation commands **only if they do not modify tracked project files**.
* Use temporary files outside the repository if a diagnostic tool absolutely requires them.
* Inspect runtime/test output.
* Inspect logs generated outside tracked source files.

You MUST NOT:

* Modify source code.
* Modify tests.
* Modify documentation other than the designated audit report.
* Modify configuration.
* Upgrade dependencies.
* Install fixes.
* Reformat files.
* Run auto-fix modes.
* Apply migrations.
* regenerate checked-in artifacts.
* Commit changes.
* Push changes.
* Create branches.
* delete files.
* rename files.
* move files.
* modify Git state.
* run destructive Git commands.
* automatically repair anything you discover.

## THE ONLY PERMITTED WRITE

The **only repository file you are allowed to create or modify is:**

`CODEBASE_AUDIT.md`

Everything you discover must be documented there.

Before finishing, run:

```bash
git status --short
```

Verify that the **only intentional repository modification is `CODEBASE_AUDIT.md`**.

If another tracked or untracked repository file was accidentally modified/generated during auditing, restore/remove that accidental artifact before completion **only to return the repository to its original state**.

Do not modify pre-existing user changes.

# 31. FINDING QUALITY STANDARD

Do not fill the report with low-value speculation.

Every substantial finding should answer:

1. **What is wrong?**
2. **Where is it?**
3. **Why is it wrong?**
4. **Under what conditions does it matter?**
5. **What is the consequence?**
6. **What evidence supports the finding?**
7. **How should it eventually be addressed?**
8. **How confident are you?**

Where useful, cite:

* file path
* symbol/function/class
* line or approximate line range
* related files
* tests
* configuration
* command output

Prefer evidence such as:

> `src/foo.ts:120-161` writes state before `bar()` succeeds, while the retry path at `src/retry.ts:88-104` re-enters the same operation without an idempotency guard.

over:

> Error handling could be improved.

# 32. SEVERITY MODEL

Assign every actionable finding one of:

## CRITICAL

Likely to cause or permit:

* catastrophic data loss
* severe security compromise
* unrecoverable corruption
* widespread production failure
* violation of a core system guarantee

## HIGH

Material defect likely to cause:

* incorrect behavior
* major reliability failure
* security exposure
* significant data-integrity problems
* major functional breakage
* serious performance/scalability limitation

## MEDIUM

Meaningful issue affecting:

* robustness
* maintainability
* less-common correctness paths
* efficiency
* reliability
* test confidence
* architecture

but not normally catastrophic.

## LOW

Real but lower-impact weakness:

* localized maintainability issue
* minor inefficiency
* minor robustness issue
* cleanup opportunity with engineering value

## INFO / OPPORTUNITY

No present defect is demonstrated, but there is a credible opportunity to:

* simplify
* optimize
* improve architecture
* reduce future risk
* improve observability
* improve developer experience

Do not inflate severity.

---

# 33. CONFIDENCE MODEL

Assign:

* **High confidence** — directly demonstrated by code/tests/runtime evidence.
* **Medium confidence** — strongly supported but depends on runtime/environment assumptions.
* **Low confidence** — plausible concern requiring targeted verification.

Low-confidence findings must be clearly labeled as such.

Do not present speculation as fact.

---

# 34. DEDUPLICATION

Do not report the same root cause repeatedly.

If one architectural defect creates 12 manifestations:

* create one primary finding
* list affected locations/examples underneath
* describe the blast radius

Use separate findings only when remediation or consequences materially differ.

# 35. PRIORITIZE ROOT CAUSES

Prefer:

> Shared operation state has no durable idempotency boundary, producing several retry/restart bugs.

over 15 separate observations describing symptoms of that same flaw.

Look for **systemic causes**.

# 37. AUDIT DEPTH REQUIREMENT

Do not stop after finding the first few significant issues.

Continue inspecting the **rest of the repository**.

Finding Critical or High issues early does not terminate the audit.

Likewise, passing tests does not terminate the audit.

Continue until you have examined all meaningful first-party areas of the repository.

# 38. DO NOT EQUATE SEARCH WITH REVIEW

Searching for:

```text

FIXME
any
catch
unsafe
deprecated
```

is useful but insufficient.

You must actually reason about code.

Read surrounding implementations.

Follow callers and callees.

Trace important workflows.

Compare duplicated rules.

Inspect error paths.

Inspect lifecycle behavior.

Inspect tests.

Inspect configuration.

Inspect persistence.

Inspect architecture.

The objective is **semantic review**, not keyword collection.

# 39. USE MULTIPLE AUDIT PASSES

Perform the audit in multiple conceptual passes rather than one linear scan.

At minimum:

### Pass 1 — Repository mapping

Understand structure, languages, packages, applications, and architecture.

### Pass 2 — Intended behavior

Read specifications, docs, schemas, contracts, and tests.

### Pass 3 — Core correctness

Trace important workflows and invariants.

### Pass 4 — Failure behavior

Study retries, restart, errors, partial failure, malformed inputs, and edge cases.

### Pass 5 — Concurrency and state

Study async execution, ownership, lifecycle, event ordering, and races.

### Pass 6 — Security/privacy

Study trust boundaries and sensitive data.

### Pass 7 — Performance/scalability

Study hot paths, algorithms, I/O, queries, network behavior, and memory.

### Pass 8 — Architecture/maintainability

Challenge abstractions, boundaries, duplication, and complexity.

### Pass 9 — Test/CI/build

Determine whether existing quality gates actually protect the system.

### Pass 10 — Cross-cutting consistency

Search globally for divergent implementations of the same concepts.

### Pass 11 — Findings challenge

Try to disprove your own findings.

Remove or downgrade findings whose evidence is weak.

### Pass 12 — Coverage pass

Review the repository map again and identify anything you have not meaningfully inspected.

Do not finalize until this last coverage pass is complete.

# 40. ADVERSARIAL REVIEW

Approach important code as if you were deliberately trying to make it fail.

Ask:

* What input did the author probably not consider?
* What sequence did the author probably not test?
* What if this happens twice?
* What if it happens simultaneously?
* What if it succeeds halfway?
* What if the application crashes immediately afterward?
* What if the callback arrives much later?
* What if state changed while awaiting?
* What if this data comes from an older version?
* What if a field is missing?
* What if a field is unexpectedly present?
* What if there are zero records?
* One record?
* Millions?
* What if the clock changes?
* What if ordering changes?
* What if the dependency responds slowly?
* What if the same event is replayed?
* What if two users/processes/devices modify the same state?
* What if cleanup runs twice?
* What if cleanup never runs?

Use these questions to discover issues; do not merely copy them into the report.

# 41. CHALLENGE EACH FINDING

Before recording a serious finding:

1. Re-read the relevant code.
2. Search for guards elsewhere.
3. Search callers.
4. Search tests.
5. Search configuration that could invalidate your assumption.
6. Check whether behavior is intentional/documented.
7. Determine realistic reachability.
8. Determine realistic impact.
9. Adjust severity and confidence accordingly.

Avoid false positives.

A smaller number of **well-proven** findings is more valuable than hundreds of generic recommendations.

At the same time, do not suppress valid findings merely because they require complex reasoning.
