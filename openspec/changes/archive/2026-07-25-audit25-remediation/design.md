## Decisions

### AUDIT25-01 — Debounced hidden-window journal

- **Decision (revised mid-implementation — see below)**: `WindowShepherdService` holds the journal in memory (`HiddenWindowJournalFile? _journalCache`, loaded once lazily via `GetJournalCache()` rather than re-reading `hidden-windows.json` from disk on every call — this half of the fix applies uniformly and has no downside). On top of that in-memory cache, `JournalHide` and `JournalClear` are treated **asymmetrically**, not identically:
  - `JournalHide` (a guest just became hidden) writes to disk **synchronously**, immediately — no debounce.
  - `JournalClear` (a guest just became visible again) writes to disk through a debounced `DispatcherTimer? _journalDebounce` (~300ms), mirroring `GroupManager.RequestSave` (`Services/GroupManager.cs:54-67`).
- **Why the split, not a uniform debounce of both (discovered during implementation, not anticipated in the original proposal/design)**: `Process.Kill()` and Task Manager's "End Task"/`taskkill /F` call Win32 `TerminateProcess` — an immediate, unconditional kill that allows **zero user-mode code to run afterward**. No `finally` block, no `AppDomain.UnhandledException`, no `Application_Exit`. None of the 5 `App.xaml.cs` handlers `FlushJournal()` is wired into (see below) can run in that case, because by definition nothing can. That matters because a hard force-kill is *exactly* the scenario the journal exists for (per its own doc comment, and the existing ValidationDriver `crashkill-rescue` scenario, which force-kills via a real `TerminateProcess`) — so debouncing `JournalHide` would have silently reopened a gap in the one guarantee this journal is built around, with no way for any exit-handler wiring to close it. `JournalClear` doesn't have this problem: `RescueOrphanedWindows` unconditionally `ShowWindow`s every journaled entry regardless of its *current* visibility, so a stale clear caught mid-debounce by a force-kill just causes a harmless redundant re-show on the next rescue — never a missed rescue. This asymmetry is why only `JournalClear` debounces.
- **Why this over alternatives**: The audit itself proposes three options for the *original* (uniform) framing — (a) debounce (chosen, now refined into the split above), (b) `Task.Run` fire-and-forget with a lock, (c) purely in-memory during the session with periodic + exit-path flush only. The split preserves the "cheap, already-proven pattern, no new concurrency primitives" property the audit favored, while additionally preserving full crash-recovery strength for the force-kill case that a uniform debounce would have weakened.
- **Second-order correction, found during pre-archive review (not by the user, by re-tracing every `JournalClear` call site on request)**: "debounce is safe because the guest ends up genuinely visible" is true for `PositionAndShow`'s clear and `Release(show: true)`'s clear, but **false** for the third call site: `Release(window, show: false)` — the guest-initiated-hide (tray-style close) path, where the guest ends up **intentionally hidden**, not visible. A stale "hidden" entry surviving a crash there is indistinguishable from a real orphan and would get incorrectly un-hidden by `RescueOrphanedWindows` — a genuine unwanted-reappear regression, not a harmless no-op. Concrete failure sequence: guest W is hidden as an inactive tab (`JournalHide(W)` written synchronously) → user switches back to W (`PositionAndShow` → `JournalClear(W)` debounced, pending) → W hides itself within that window (`Release(W, show:false)` → `JournalClear(W)`, also debounced under the original split) → force-kill before either debounced write lands → W's stale "hidden" entry from the *first* write is still on disk → next-launch rescue incorrectly shows W.
  - **Fix**: `JournalClear` gained an `immediate` parameter (default `false`, preserving the debounce for the two genuinely-safe call sites). The `Release(show: false)` call site alone passes `immediate: true` — it stops any pending debounce timer and calls `SaveJournal` synchronously on the *current* in-memory state, which already has W's entry removed by that point. This guarantees the on-disk journal has no entry for W by the time `Release` returns, regardless of what debounce timing existed beforehand — the synchronous write flushes the whole current state, not just this one entry.
  - **Verified**: new ValidationDriver scenario `crashkill-selfhide-not-rescued` reproduces the exact sequence above (hide → switch back → self-hide → immediate force-kill → relaunch) and asserts no `SHEPHERD[rescue]` line appears at all (proving the journal was already empty, not "would eventually become empty") and the self-hidden guest is never resurrected. Passes.
- **Crash-flush requirement (RESOLVED — all five paths)**: All five `App.xaml.cs` exit/crash paths (`Application_Exit`, `Application_DispatcherUnhandledException`, `CurrentDomain_UnhandledException`, `Application_SessionEnding`, and the early-startup-failure path) call a new `WindowShepherdService.FlushJournal()` that stops the debounce timer (if pending) and synchronously writes the in-memory journal state immediately — the same shape as `GroupManager.SaveState()` already does relative to `RequestSave()` (`Services/GroupManager.cs:40-44`). Given the split above, this call only ever has a pending *clear* to flush (never a pending hide) — it exists to make graceful exits/managed exceptions tidy (no lingering stale-but-harmless clear entries across a restart), not to protect the force-kill case, which `JournalHide`'s synchronous write already fully covers on its own.
- **What does not change**: The on-disk journal file format (`HiddenWindowJournalFile`/`HiddenWindowEntry`), `LoadJournal`'s corrupt-file handling, `RescueOrphanedWindows`' validation logic, and the `.tmp` + `File.Move(overwrite:true)` atomic-write pattern inside `SaveJournal` — only the *cadence* of `JournalClear`'s writes changes; `JournalHide`'s cadence is unchanged (still synchronous), only its *cost* drops (no more disk read on every call, since the in-memory cache serves it).

### AUDIT25-02 — Exe-path icon cache

- **Decision**: Add an instance-level `Dictionary<string, ImageSource?> _iconCache` to `IconService` (`Services/IconService.cs`), keyed by the resolved exe path. `GetFileIcon(string exePath)` checks the cache first; on a miss, runs the existing `ExtractIconEx`/`CreateBitmapSourceFromHIcon` path and stores the result (including a cached `null` for exe paths that fail to yield an icon, so a broken/inaccessible exe isn't retried every refresh). `GetWindowIcon(IntPtr hwnd)` is unchanged except that it now benefits transitively from the cache inside `GetFileIcon`.
- **Why this over full async loading**: The proposal scopes this change to the cache only. The audit frames the cache as strictly cheaper and lower-risk ("a smaller, lower-risk fix than full async loading and could be done first as a quick win, with async loading as a follow-up"). A typical desktop session has many windows but few distinct executables (browser, terminal, IDE), so the cache captures most of the win with no `Refresh()` control-flow changes and no XAML/binding changes.
- **Lifetime**: `IconService` is constructed once in `App.xaml.cs` and lives for the process lifetime (same as today), so the cache persists across picker opens — an icon extracted once is never re-extracted for the same exe path for the rest of the session. No eviction policy: the working set (distinct exe paths seen) is bounded by how many distinct applications the user runs, which is small relative to memory cost of a handful of cached `ImageSource` bitmaps.

### AUDIT25-05 — Coalesced activation timers

- **Decision**: Add two new fields to `ContainerWindow`: `DispatcherTimer? _activateReassertTimer` (for the `WM_ACTIVATE` handler at `Views/ContainerWindow.xaml.cs:142-164`) and `DispatcherTimer? _stateSettledTimer` (for `ContainerWindow_StateChanged`'s snapshot timer at `:313-319`). Each call site stops-and-replaces its own field instead of allocating a bare local `var timer`, matching `App.xaml.cs`'s `DebounceNameChanged` shape (`_nameChangeDebounce` dictionary keyed by hwnd — here a single field suffices since each `ContainerWindow` instance only ever tracks its own single shepherded active window/state, not a per-hwnd map).
- **Why two separate fields, not one shared timer**: The two timers serve different call sites with different intervals (120ms re-assert vs. 750ms settle snapshot) and different purposes (correctness-adjacent re-assertion vs. pure diagnostic logging) that can legitimately be in flight concurrently (an activation and a maximize/restore can happen close together). Coalescing them into a single shared timer would conflate two unrelated debounce semantics for no benefit.
- **No behavior change to the re-assert logic itself**: The existing re-check (`_shepherdActiveWindow == activeWindow && IsWindowVisible(...)`) inside the timer callback is preserved verbatim — only the timer's lifecycle (allocated fresh vs. stopped-and-reused) changes.

### Item #6 — `PickColorCommand`

- **Decision (RESOLVED — option (a), bug-only no-op)**: `PickColorCommand`, along with `StartRenameCommand`/`FinishRenameCommand`/`CloseGroupCommand`, is confirmed unbound in any `*.xaml` file (repo-wide search found no `PickColor`/`ColorPick` reference outside `GroupViewModel.cs` and the tracking docs). The fix is a documented no-op: remove the `AddWindowsRequested` invocation from `PickColorCommand`'s handler (`ViewModels/GroupViewModel.cs:103`) and replace it with a comment explaining the command is an intentional, inert placeholder pending future UI wiring. No `AccentColor` cycling, no new preset palette, no other behavior change.
- **Why not option (b) (accent-color cycling)**: Rejected — it would give a completely unbound, unreachable command fake-real behavior that looks like it does something when nothing in the UI can ever trigger it. A future reader seeing "cycles through presets on `Execute()`" would reasonably assume a UI path calls it; there isn't one. The bug-only fix is honest about the command's current inert state and fully closes the actual bug (wrong target invoked) without manufacturing observable-looking behavior nobody can reach.

## Risks / Trade-offs

- **[Risk] A uniform debounce of both JournalHide and JournalClear would have reopened the crash-recovery gap for hard force-kills (Process.Kill()/Task Manager "End Task"/taskkill /F), since TerminateProcess allows no App.xaml.cs handler to run and so no amount of exit-path wiring could flush a pending debounced hide before death** → Mitigated by design: `JournalHide` stays synchronous (never debounced) specifically because it's the one write that must precede an unpredictable future force-kill; only `JournalClear` debounces, which is safe to delay since a stale clear only causes a harmless redundant re-show, never a missed rescue (`RescueOrphanedWindows` doesn't check current visibility before re-showing). The 5-path `FlushJournal()` wiring remains useful for tidiness on managed/graceful exits, but the crash-recovery guarantee itself does not depend on it. The ValidationDriver regression scenario (task 5.5: force-kill immediately after rapid tab switches, no settle time) verifies this holds.
- **[Risk] AUDIT25-02's cached `null` for a failed icon extraction could mask a transient failure (e.g., a locked file) that would have succeeded on retry** → Mitigation: accepted trade-off — icons are cosmetic (per the audit: "worst case on a bug is a blank/default icon, not incorrect capture behavior"), and the cache is process-lifetime only (a full app restart clears it).
- **[Trade-off] AUDIT25-05's two independent timer fields are slightly more code than one generic "debounce helper" utility** → Accepted: the audit explicitly frames this as "optional polish," and a shared generic debounce helper is a larger abstraction than the two one-line `Stop()`-then-reassign fixes actually needed; introducing one now would be scope creep beyond what either call site requires.

## Migration Plan

No data migration. No persisted-file schema changes. Rollout is a normal code change/build/release; rollback is a normal revert (no forward-only data changes to undo). The one operationally relevant change is AUDIT25-01's write cadence — if a rollback is ever needed, reverting the debounce simply restores today's synchronous-write behavior with no journal-file compatibility concern in either direction (both versions read/write the same `HiddenWindowJournalFile` shape).
