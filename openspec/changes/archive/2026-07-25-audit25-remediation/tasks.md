## 5. AUDIT25-01 — Debounced hidden-window journal (Open Decision #1 resolved: all five paths)

- [x] 5.1 Confirmed with the user: wire `FlushJournal()` into all five candidate paths (`Application_Exit`, `Application_DispatcherUnhandledException`, `CurrentDomain_UnhandledException`, `Application_SessionEnding`, and the early-startup-failure path) — not a subset. `FlushJournal()` is a no-op when nothing is pending, so this costs nothing extra.
- [x] 5.2 **Revised mid-implementation — flagged and confirmed with the user rather than resolved silently** (see design.md AUDIT25-01 decision): a uniform debounce of both `JournalHide` and `JournalClear` would have reopened the crash-recovery gap for hard force-kills (`Process.Kill()`/Task Manager "End Task"/`taskkill /F` all invoke `TerminateProcess`, which runs no `App.xaml.cs` handler whatsoever — no exit-path wiring could flush a pending debounced hide before such a kill). Implemented instead: both `JournalHide`/`JournalClear` (`Services/WindowShepherdService.cs`) mutate an in-memory `HiddenWindowJournalFile` (`GetJournalCache()`, loaded once, not re-read from disk per call) — but only `JournalClear` debounces its write via a new `_journalDebounce`/`RequestJournalSave()` (300ms, mirroring `GroupManager.RequestSave`); `JournalHide` still calls `SaveJournal()` synchronously on every call, since `RescueOrphanedWindows` re-shows unconditionally regardless of current visibility, making a stale *clear* harmless but a missed *hide* not.
- [x] 5.3 Add a `FlushJournal()` method to `WindowShepherdService` that stops any pending debounce timer and calls `SaveJournal()` synchronously and immediately, mirroring how `GroupManager.SaveState()` relates to `RequestSave()` (`Services/GroupManager.cs:40-44`). (Given 5.2's split, this only ever has a pending clear to flush.)
- [x] 5.4 Wire `FlushJournal()` into all five `App.xaml.cs` paths confirmed in 5.1: `Application_Exit` (`:133-152`), `Application_DispatcherUnhandledException` (`:154-169`), `CurrentDomain_UnhandledException` (`:171-184`), `Application_SessionEnding` (`:186-200`+), and the early-startup-failure path (`:118-130`), via a new `FlushJournalGuarded(context)` helper mirroring `SaveStateGuarded`.
- [x] 5.5 Added `crashkill-rapidswitch-rescue` scenario to `tests/ValidationDriver/TabDock.ValidationDriver/Scenarios.cs` (registered in `StandaloneExtraScenarios` and `RunScenario`'s switch, alongside the existing `crashkill-rescue`): fires a rapid, no-settle-time burst of 6 tab-switch clicks, force-kills immediately after the last one (before the ~300ms `JournalClear` debounce could possibly elapse), relaunches, and asserts the pig left hidden by the final switch is still rescued. No other `tests/ValidationDriver/**` changes made.
- [x] 5.6 Confirmed `HiddenWindowJournalFile`/`HiddenWindowEntry`'s on-disk shape, `LoadJournal`'s corrupt-file handling, and `RescueOrphanedWindows`' validation logic are untouched by 5.2-5.4 — only `JournalClear`'s write cadence and the removal of per-call `LoadJournal()` disk reads changed.
- [x] 5.7 **Second correction, found during pre-archive review** (see design.md AUDIT25-01 decision): re-tracing every `JournalClear` call site found that `Release(window, show: false)` (guest-initiated hide / tray-style close) is NOT safe to debounce like `PositionAndShow`/`Release(show: true)` are — the guest there ends up intentionally *hidden*, so a stale on-disk entry surviving a crash would cause `RescueOrphanedWindows` to incorrectly un-hide it, a real regression, not a harmless no-op. Fixed: `JournalClear` gained an `immediate` parameter (default `false`); the `show: false` release path alone passes `immediate: true`, stopping any pending debounce and flushing the current in-memory state synchronously.
- [x] 5.8 Added `crashkill-selfhide-not-rescued` ValidationDriver scenario (registered alongside `crashkill-rescue`/`crashkill-rapidswitch-rescue`): reproduces hide → switch-back (clear debounced-pending) → guest self-hide (immediate clear) → force-kill → relaunch, and asserts no `SHEPHERD[rescue]` line appears at all and the self-hidden guest is never resurrected. Passes — confirms 5.7's fix closes the gap.
