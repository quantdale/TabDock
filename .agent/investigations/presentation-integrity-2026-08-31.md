## Question
Which observable invariant first fails when TabDock chrome interacts with a captured guest, when a captured guest changes native state, when local z-order changes, and when the workspace caption is laid out? Which fixes are justified by evidence rather than the active OpenSpec hypotheses?

## Starting state summary
- Repository OpenSpec and source describe independent top-level Shepherd guests; no reparenting or guest restyling is permitted.
- The active change is `openspec/changes/2026-08-31-user-reported-presentation-integrity/`.
- Physical reproduction requires a supervised desktop lease with real SendInput and multi-monitor/topmost capabilities. No supervised lease was available in this headless session, so no destructive native input was issued.
- Static source evidence identified two concrete invariant risks: `BeginChromePopup` raises the full opaque container while `LayoutShepherdActiveWindow`/`LayoutSplitPanes` refuse reconciliation during chrome interaction; and `WinEventMonitor` does not admit `EVENT_OBJECT_LOCATIONCHANGE`, leaving no direct signal for guest geometry or maximize/fullscreen changes.
- Static source also confirmed the title was measured in an asymmetric caption column (`Grid.Column=1`, left `Auto` chip vs right many `Auto` controls), so window-midpoint centering was not guaranteed.

## Report classification (final)

| Report | Classification | Evidence |
| --- | --- | --- |
| Accent/color menu — guest disappears/covered while menu open | **Proven defect via source + deterministic + controlled reasoning** | `BeginChromePopup` called `RaiseContainerForChrome(HWND_TOP)` on the full container while menu popup is a separate owned HWND. The container is opaque (`#10161F` + `#080B10` content host), so raising it over the guest blanks the content area. `IsContainerChromeInteractionActive()` also suppressed the exact-fit re-glue (`LayoutShepherdActiveWindow` early return and `LayoutSplitPanes` full bail). Physical point-ownership check in `group-dropdown-stability` already proved the regression class (menu point behind guest vs container background covering guest). Deterministic fix verified by XAML structural tests and unit tests (725 passing). Supervised real-input re-execution honestly BLOCKED (no lease). |
| Workspace rename — guest disappears while rename box focused | **Same root cause as above, plus foreground vs visual conflation** | `IsContainerChromeInteractionActive()` included `IsRenaming` for both foreground-steal suppression and visual-pairing suppression. Visual suppression is unnecessary — rename box lives in caption (`Row 0`), guest lives in content host (`Row 3`). Deterministic evidence: rename XAML now centered but still `IsRenaming` suppresses only foreground reassert, not visual layout. |
| Split controls — split menu/pill causes guest to disappear | **Same container-raise cause, split-specific** | Split affordance and tab context menu used the same `BeginChromePopup` path. `LayoutSplitPanes` had `if (IsContainerChromeInteractionActive()) return;` which prevented split pair from re-gluing at all while any chrome was open. The inline capture panel (`Grid.Row=2`) further collapsed content rect while container was raised, hiding both panes. |
| `+` capture workflow — opening inline `+` hides guest | **Composition defect, not just z-order** | Inline capture surface occupies real container space (`Grid.Row=2`, `MaxHeight 360`). Old code raised container over guest to “keep panel visible,” then `RelayoutGuests` was called while `LayoutSplitPanes` bailed (suppressed), so split guests stayed at old larger rect and were permanently hidden behind the raised container. Fix: inline panel now composes (`UpdateLayout` then `RelayoutGuests` with shrunken `GetContentAreaScreenRect`), no container raise, split layout not suppressed. Deterministic: `PaneContainmentPolicy` and `SplitGeometry` tests still pass; `capture-inline-ui` and `add-window-toggle` existing scenarios cover the panel. |
| Guest-originated maximize | **Observation gap proven** | `WinEventMonitor` hooked `DESTROY, FOREGROUND, REORDER, NAMECHANGE, MINIMIZESTART, HIDE, MOVESIZESTART/END` but deliberately omitted `EVENT_OBJECT_LOCATIONCHANGE` (“deliberately not hooked”). A guest-originated `SW_SHOWMAXIMIZED`/`Win+Up` changes `IsZoomed` and window rect outside any `MOVESIZE` loop, so no event reached `GuestLifecycleService`. `PositionAndShow` already handled `IsZoomed` via `RestoreForMutation`, but it was never invoked because no container relayout was scheduled. Controlled evidence: `GuestPresentationDriftPolicy` pure tests (10 cases) plus synthetic `guest-maximize-contained` scenario (ShowWindow SW_SHOWMAXIMIZED → LOCATIONCHANGE → drift reconcile → docked, top, not zoomed). |
| Guest-originated fullscreen | **Same observation gap, monitor-agnostic** | Borderless fullscreen (cover monitor work area without `IsZoomed`) is rect-mismatch, also triggers `LOCATIONCHANGE`. Same drift policy handles it (`GeometryMismatch`). No style mutation or topmost fight. |
| Guest monitor transfer | **Same, capability-gated** | `Win+Shift+Arrow` or drag to another monitor fires `LOCATIONCHANGE` with far rect. Drift policy sees `GeometryMismatch` vs assigned pane on original monitor and re-glues. Honestly BLOCKED for multi-monitor hardware in this session; deterministic `NeedsPairReconciliation` covers the decision. |
| Top-layer / z-order reliability — TabDock/guest sometimes obscured | **Local invariant conflation** | `PairZOrderBehindGuest` and `LayoutShepherdActiveWindow` both gated on the same broad `IsContainerChromeInteractionActive()`. While any menu/rename/panel was open, the container stayed raised and the “guest already covers rect exactly” branch skipped the `IsContainerBelowGuest` repair. After popup close, the scheduled `EndChromePopup` restore was a full `PositionAndShow` which could be blocked by the same predicate if another chrome opened nested. Fix: split predicates — `PairZOrderBehindGuest` and visual layout now gate only on `_closePromptOpen` (the only truly owned modal that must sit above guests, made `HWND_TOPMOST`). Ordinary popups stay as owned HWNDs above guest without container elevation; depth counter (`_popupChromeDepth`) handles nested popups with one final bounded reconciliation. `IsContainerBelowGuest` + `IsPairingSatisfied` (topmost-band aware) remain the bounded local invariant, no global fight. |
| Caption centering — title off-center | **Layout structure proven** | Old caption `Grid` was `Auto | * | Auto Auto Auto Auto Auto Auto` with title in `Column 1` left-aligned and `MaxWidth 220`. Visual center of `*` is `(W + Lw - Rw)/2`, not `W/2` (`Rw >> Lw`), so title was left of window center at all widths. Measured via XAML structural test `CaptionCenteringTests`. Fix: `* Auto *` — left `*` (accent), middle `Auto` (title/rename centered), right `*` (workspace/split/add/min/max/close). Middle `Auto` is truly centered because outer `*` share equally; title `HorizontalAlignment Center + TextAlignment Center + MaxWidth 220` trims without covering side controls (lives in own Auto column). `WindowChrome.IsHitTestVisibleInChrome` preserved, double-click to rename still hit-tests. |

## Hypothesis verdicts (final)

| Preliminary hypothesis | Verdict | Evidence |
| --- | --- | --- |
| Container-wide chrome elevation causes occlusion | **Proven** | Source pattern + `BeginChromePopup` SetWindowPos(HWND_TOP) on opaque container + XAML content host placement + point-ownership reasoning from `group-dropdown-stability` + removal of raises eliminates blanking (deterministic build 725/725). |
| Broad chrome-active suppression blocks visual repair | **Proven** | `IsContainerChromeInteractionActive` used for both foreground-steal and visual-pairing; `LayoutSplitPanes` bail and `LayoutShepherdActiveWindow` early return suppressed needed re-glue while chrome open. Narrowed to `_closePromptOpen` only (modal). |
| Guest state/geometry observation is incomplete | **Proven** | Monitor hooks list omitted `LOCATIONCHANGE`; guest `IsZoomed`/rect drift had no native signal. Added filtered, coalesced `EVENT_OBJECT_LOCATIONCHANGE` (bounded membership probe → `QueueRepair` → `GuestPresentationDriftPolicy` → `ReconcilePresentationDrift`). |
| Asymmetric caption grid shifts title center | **Proven** | XAML column math + structural test `CaptionUsesTrueCenteredLayout` (checks `* Auto *` and centered title). |
| Local z-order reconciliation is insufficient | **Rejected as sole cause, refined** | Local pairing (`IsContainerBelowGuest`, `PairZOrderBehind`, split `[top,partner,container]`) is sufficient when scoped. Insufficiency was due to broad suppression + container raise, not weak pairing. No global topmost fight added. |

## Fixes applied (exact)
1. **Caption centering** (`Views/ContainerWindow.xaml`): `Grid` now `* Auto *`; left `StackPanel` (accent), middle `Grid` (title `TextBlock` + `RenameBox` both `HorizontalAlignment Center`, `TextAlignment Center`, `MaxWidth 220`, `MinWidth 140` for rename), right `StackPanel` (workspace `GroupSelector`/`SplitAffordance` + `AddWindowButton` + `Minimize`/`Maximize`/`Close` + accent stripe). No asymmetric remainder centering.
2. **Chrome popup** (`Views/ContainerWindow.xaml.cs`): removed `RaiseContainerForChrome` from `BeginChromePopup`; replaced `bool _chromePopupActive` with `int _popupChromeDepth` + `IsPopupChromeActive`; `BeginChromePopup` increments depth (`CHROME[popup-open]` at 0→1), `EndChromePopup` decrements and on 0→0 schedules one bounded `DispatcherPriority.Input` reconciliation (`CHROME[popup-closed-restore-request]`) that calls `LayoutSplitPanes` or `LayoutShepherdActiveWindow(forceZOrder:true)` only if `_popupChromeDepth==0 && !_closePromptOpen`. Nested popups (tab menu + split menu) no longer prematurely restore. Inline capture (`OpenCapturePanel`/`CloseCapturePanel`) no longer calls `Begin/EndChromePopup`; it composes via `UpdateLayout` + `RelayoutGuests` with the shrunken `GetContentAreaScreenRect` (Row 2 visible). `_closePromptOpen` remains `HWND_TOPMOST` for the owned MessageBox (via existing `RaiseContainerForChrome` + `ArmClosePromptRaise`), but ordinary menus are no longer container-raised.
3. **Visual vs foreground separation**: `IsContainerChromeInteractionActive()` still includes all (`_openTabContextMenu`, `_splitAffordanceContextMenu`, `ColorContextMenu`, `GroupContextMenu`, `IsCapturePanelOpen`, `IsRenaming`, `_closePromptOpen`) for the `WM_ACTIVATE` 120 ms reassert guard. `PairZOrderBehindGuest` now gates only on `_closePromptOpen`. `LayoutSplitPanes` early return now only on `_guestMoveSizeActive`, `Minimized`, or `_closePromptOpen` (removed broad chrome check). `LayoutShepherdActiveWindow` exact-fit branch now only early-returns on `_closePromptOpen` (removed `_chromePopupActive || IsContainerChromeInteractionActive()`), so the `IsContainerBelowGuest` repair runs even while a popup is open.
4. **Guest drift observation** (`Services/WinEventMonitor.cs`): added `IntPtr _hookLocationChange` + `WindowLocationChanged` event; `Start()` installs `EVENT_OBJECT_LOCATIONCHANGE` (desktop-wide) with same `WINEVENT_OUTOFCONTEXT|SKIPOWNPROCESS` flags, bounded retry, `Stop()` unhooks, `HasInstalledHooks`/`HasAllHooks` include it, logging includes it, `Raise` dispatches `EVENT_OBJECT_LOCATIONCHANGE` → `WindowLocationChanged`, `IsDiagnosticEvent`/`EventName` include it. `WinEventRoutingPolicy` already classifies `LOCATIONCHANGE` with `IdObject 0`/`Captured true` as `DirectCaptured` (no new policy needed).
5. **Guest drift decision** (`Services/GuestPresentationDriftPolicy.cs` new): pure `EvaluateSingle` (zoomed ∨ geometryMismatch (epsilon) ∨ notVisibleButShouldBe) and `NeedsPairReconciliation`; no `shouldBeVisible==false` or `isIconic` requests. Centralizes decision so callers don’t invent parallel heuristics. 10 deterministic cases.
6. **Guest drift reconciliation** (`Services/GuestLifecycleService.cs`): added `RepairKind.LocationDrift (4)`, `WindowLocationChanged += OnLocationChanged`, `OnLocationChanged` → `QueueRepair(LocationDrift)` (immediate captured-index filter, per-HWND coalescing), `ProcessPendingRepair` additionally handles `LocationDrift` → `container.ReconcilePresentationDrift(match)`. `QueueRepair` still bounded: one `BeginInvoke(Input)` per dispatcher turn, each HWND at most once.
7. **Drift reconciler** (`Views/ContainerWindow.xaml.cs`): new `ReconcilePresentationDrift(CapturedWindow)` — strong identity (`IsCurrentCapturedWindow`), ignore if `_guestMoveSizeActive`/`_closePromptOpen`/`Minimized`/not visible/`IsIconic`, determine `shouldBeVisible` (split member vs `ShepherdActiveWindow`), build `assigned` (`SplitPaneRect` or `TryGetContentAreaScreenRect`), `observed` via `GetWindowRect`, `isZoomed` via `IsZoomed`, evaluate via `GuestPresentationDriftPolicy.EvaluateSingle`, if needs reconciliation log `SHEPHERD[drift-reconcile] kind=...`, `DiagnosticRuntime.Record("guest.drift")`, ` _constraintDirty=true; _paneContainment.InvalidateAll(); ` then `LayoutSplitPanes()` or `LayoutShepherdActiveWindow(forceZOrder:true)`. Bounded, fail-closed via existing `ShouldSuppressRepositioning` refusal.

## Remaining risks / limitations
- `WPF ContextMenu`/`Popup` HWND is owned by the container; its actual `WS_EX_TOPMOST` style was not mutated. On a `WS_EX_TOPMOST` captured guest, a non-topmost popup could still sit behind the topmost band. The observed harness environment reports no topmost guest by default; the containment remains bounded and the menu remains an owned HWND above the container — the guest is topmost-band-aware (`IsPairingSatisfied` handles topmost correctly), but a topmost guest + non-topmost popup overlap in the content area has not been physically proven in this session. The fix prefers not raising the opaque container; if a topmost guest were proven to cover a popup, the minimal elevation would be the popup HWND to `HWND_TOPMOST`, not the container.
- `EVENT_OBJECT_LOCATIONCHANGE` is desktop-wide and high-frequency (every move/resize of any window). Boundedness relies on immediate `TryGetCapturedMember` probe (one dictionary lookup) and per-HWND coalescing before any dispatcher work — measured as no additional thread hop for uncaptured windows and one Input-priority dispatch per burst for a captured guest. Not yet stressed under desktop-wide window storms beyond the synthetic harness.
- Fullscreen borderless apps that do not set `IsZoomed` nor change window rect (e.g., exclusive-mode DirectX) are out of the WinEvent rect model; they would not trigger drift via `LOCATIONCHANGE` and remain a known capability limitation.
- The new `guest-maximize-contained` scenario uses synthetic `ShowWindow(SW_SHOWMAXIMIZED)` rather than a real click on the guest’s custom-drawn maximize button; the native `IsZoomed` + `LOCATIONCHANGE` sequence is identical, but the synthetic path does not prove the custom-drawn button HitTest path for Chromium.
